# Headless SEO Inspector — Product Requirements Document

**Версия:** 1.0 · **Дата:** 14.10.2026 · **Статус:** согласование перед разработкой · **Приоритет:** MVP

> **Базовые решения пользователя (утверждены):** поддержка любых headless-фронтендов; Docker; получение данных backend только через API/JSON; полный каталог + категории + информационные страницы; хранение результатов только в JSON/CSV/HTML (включая JSONL); без исполнения JavaScript и браузерного сканирования в MVP; веб-панель с первой версии.
>
> **(!!!!!)** — архитектурное предположение, оценка или гипотеза, которую требуется подтвердить на пилоте. Доказанные факты из SABOSPORTS отделены от универсальных правил.

## 1. Резюме продукта

Headless SEO Inspector (HSI) — самодостаточный сервис для технического анализа публичного HTML и HTTP-ответов сайта, с дополнительной возможностью сопоставить найденные страницы с каталогом или контентом backend через read-only API/JSON. Сервис не зависит от Next.js, Битрикса и конкретной CMS.

Инструмент предназначен для выявления **воспроизводимых технических дефектов**: неожиданных HTTP-статусов; неработающих внутренних ссылок; неконсистентности редиректов, canonical и sitemap; ошибок индексируемости; структурированных данных; отсутствия важных тегов; противоречий между backend и фронтендом. Находки сопровождаются доказательствами и различают «ошибку», «предупреждение», «информацию» и «недостаточно данных».

Это **не** сервис для автоматической оценки поисковых позиций, доказательства посещения Googlebot/Яндекс.Бота, аудита качества SEO-текстов и воспроизведения JavaScript-пользовательского интерфейса. Эти задачи могут появиться в V2.

## 2. Проблема и мотивация

Сторонние SEO-аудиты часто объединяют признаки, причины и рекомендации в одинаково критичные задачи. На SABOSPORTS зафиксированы реальные примеры, которые необходимо различать:

- Браузер получает HTTP 200 для страницы товара, а по отчётам Яндекс.Вебмастера и GSC поисковый робот сталкивался с HTTP 404. Скрин Chrome подтверждает только браузерный запрос; **причина расхождения не установлена**.
- В товарном JSON-LD указан `aggregateRating.ratingValue=5` без `ratingCount/reviewCount`: конкретный проверяемый дефект для Google-rich-results.
- Публичная структура URL и canonical в сохранённых файлах преимущественно без завершающего слеша; требование аудиторов включить слеш везде нуждается в проверке, а не в автоматическом исполнении.
- Старые 404 URL и неизвестные категории, ошибочно отвечающие 200 с общим каталогом, требуют разных действий.
- Двойные DOM ID, пустые декоративные `alt`, лишний `manifest`, кнопки с JS-навигацией — неравнозначные по риску дефекты.

HSI должен позволить проверить такие вопросы на **всех доступных страницах**, повторить после релиза и увидеть изменения в результатах.

## 3. Цели, границы и KPI

### 3.1 Цели MVP

1. Запустить независимую проверку любого разрешённого сайта в Docker без установки пакета в CMS.
2. Выполнить полный обход источников URL (sitemap, краулинг, API/JSON) с явным учётом неполных сканов.
3. Проверять исходный HTTP/HTML до исполнения JavaScript.
4. Сопоставлять ожидаемые сущности каталога с доступностью фронтенда при наличии backend-фида.
5. Предоставлять доступный из браузера защищённый интерфейс: проекты, запуски, ошибки, URL, фильтры, отчёты, история.
6. Экспортировать воспроизводимые доказательства проверок и изменения между запусками.
7. Обеспечить независимость ядра от конкретной CMS и структуры роутинга.

### 3.2 Критерии успеха пилота (целевые, не факты)

- 100% URL из согласованных источников обработаны, исключены по правилам или явно помечены как неуспешно проверенные. «Тихих» потерь URL нет.
- Не менее 95% заранее размеченных тестовых дефектов в фикстурах правильно классифицированы; 0 ложных P0 в обязательном наборе отрицательных кейсов.
- Два запуска на одном и том же тестовом наборе дают детерминированные ID правил/URL и стабильные результаты при одинаковых ответах.
- Первый проект разворачивается по README и Docker Compose без настройки БД и CMS.
- При полном сканировании сбой/рестарт не приводит к потере уже завершённых проверок; есть продолжение скана.
- Пользователь может за ≤ 3 клика открыть доказательства любой находки из списка проектов.

### 3.3 Не входит в MVP

- Выполнение JavaScript, снятие скриншотов, Lighthouse/Playwright, Core Web Vitals, визуальные UX-проверки.
- Подключение к БД Битрикса, Shopify и других CMS; изменение объектов backend.
- Подключение GSC/Яндекс.Вебмастера и заявления о настоящих ответах их роботов.
- Автоматический ремонт сайта, установка редиректов, модификация robots/sitemap.
- Мониторинг позиций, семантика, закупка ссылок, генерация SEO-контента, гарантия индексации.
- Полноценная многопользовательская RBAC/SSO система и публичный SaaS.

## 4. Пользователи и роли

- **Технический PM/аналитик:** создаёт проект и профиль URL, запускает аудит, оценивает масштаб, передаёт дефекты разработке.
- **Frontend/Backend-разработчик:** открывает конкретные URL, HTTP-цепочку, сниппеты HTML, сравнивает повторные запуски.
- **SEO-специалист:** видит индексируемость, canonical, sitemap, schema.org и результаты массовых проверок.
- **Администратор локальной инсталляции:** управляет доверенными доменами, секретами и сетевыми настройками.

Для MVP допускается одна роль `admin`, но анонимный доступ к сканам, конфигурациям и отчётам запрещён.

## 5. Основные пользовательские сценарии

**UC-01, подключение проекта:** администратор в панели создаёт проект, указывает публичный `baseUrl`, допустимые hostname и правила URL; проверяет доступность robots/sitemap; сохраняет профиль; ошибки конфигурации объясняются.

**UC-02, standalone-скан:** администратор запускает полную проверку. Система читает sitemap и извлекает внутренние ссылки, обходит URL по правилам, фиксирует успешные/ошибочные запросы, строит отчёт.

**UC-03, integrated-скан:** пользователь подключает read-only JSON/API-контракт. Сканер импортирует ожидаемые сущности, сравнивает статус публикации, адрес и страницу товара/категории с публичными ответами; сбои backend-фида выделяются отдельно, а не превращаются в «404 товара».

**UC-04, анализ критичного расхождения:** SEO-специалист открывает `EXPECTED_PAGE_NOT_200` и видит backend ID, ожидаемый URL, HTTP-код, последний ответ, шаг редиректа, дату и сырой факт. Если фактов недостаточно, состояние `needs_review`.

**UC-05, итерация после релиза:** PM сравнивает два законченных запуска: новые/устранённые/сохранившиеся находки, фильтрует P0/P1, экспортирует CSV/HTML для Jira.

**UC-06, расписание:** администратор задаёт cron для проекта. Очередной запуск не стартует, если предыдущий ещё идёт; история сохраняется.

**UC-07, отказоустойчивость:** при остановке контейнера после рестарта система восстанавливает очередь или помечает запуск `interrupted` с кнопкой «Продолжить»; не показывает усечённый скан как `completed`.

## 6. Функциональные требования MVP

### FR-01. Проекты и профили сайтов

- `FR-01.1` Создать/редактировать/архивировать проект с уникальным `projectId` и названием.
- `FR-01.2` Указать `baseUrl` (только HTTP(S); HTTPS предпочтителен), `allowedHosts`, языки/локали при необходимости, список стартовых URL.
- `FR-01.3` Правила нормализации настраиваются **в проекте**: trailing slash `with|without|preserve|unknown`, параметризация, допустимые query-параметры, ожидаемые canonical и необязательные исключения. Значение `unknown` не создаёт ложной ошибки.
- `FR-01.4` Настроить источники sitemap, crawl, backend API и лимиты. Поддержать несколько проектов в одной инсталляции.
- `FR-01.5` Проверить конфигурацию до запуска; токены только через env/secret-reference, без сохранения в отчётах.

### FR-02. Обнаружение и импорт URL

- `FR-02.1` Поддержать XML sitemap и sitemap index с рекурсивными ссылками в рамках допустимых хостов, gzip, UTF-8; проверить лимиты 50 000 URL / 50 МБ **на отдельный sitemap**, не на весь проект.
- `FR-02.2` Извлекать `<a href>` из исходного HTML, корректно разрешать относительные ссылки через URL базы, сохранять `sourcePage` для битых ссылок.
- `FR-02.3` Импортировать массив сущностей из API/JSON с пагинацией cursor/page. `entityId`, `type`, `url`, `publicationState` обязательны; `expectedStatus`, `expectedIndexable`, `canonical`, `updatedAt` — опционально.
- `FR-02.4` Объединить одинаковые URL из нескольких источников без утраты provenance (API, sitemap, исходная ссылка).
- `FR-02.5` Полный скан означает обработку **всего доступного набора** при согласованных границах проекта. Если лимит/таймаут/недоступный sitemap прервали discovery, статус `incomplete`, не `completed`.
- `FR-02.6` Избежать бесконечного пространства URL: не обходить query-комбинации/фасеты без явной политики; соблюдать лимиты глубины и числа URL, выдавая видимую причину ограничений.

### FR-03. Получение HTTP и HTML

- `FR-03.1` Использовать HTTP GET (не только HEAD); сохранять исходный/конечный URL, полную цепочку редиректов, HTTP-коды, Content-Type, TTFB/totalTime, размер, timestamp, безопасную выдержку HTML.
- `FR-03.2` Соблюдать robots.txt по умолчанию. Для запрещённых URL писать `skipped_robots`, не «404» и не «недоступна для индексации».
- `FR-03.3` Конкурентность, скорость, timeouts, max redirects, response size и повторы 429/5xx задаются конфигурацией; учитывать Retry-After, останавливать скан при серии отказов/429 (circuit breaker).
- `FR-03.4` Серверный HTML — единственный источник SEO-парсинга MVP. DOM после JS не реконструировать и не называть проверенным.
- `FR-03.5` Разрешить сравнение обычного и альтернативного User-Agent только как **эвристическую проверку**. Подмена заголовка не означает фактического посещения поисковым ботом.

### FR-04. Правила SEO-диагностики

- `FR-04.1` HTTP: неожиданный `404/410/5xx`, soft-404-кандидат, редирект-петля, избыточные редиректы, неверный Content-Type.
- `FR-04.2` Indexability: meta robots, X-Robots-Tag, robots-разрешение, конфликт HTTP/robots/canonical; не делать вывод «в Google проиндексировано».
- `FR-04.3` Canonical: наличие, дубли, корректный absolute URL, доступность цели, конфликт с нормализацией; canonical не равен обязательному self-canonical для всех страниц.
- `FR-04.4` Метатеги: пустые title/description, H1, необоснованные дубли по набору страниц; заголовки H1 не обязательно строго по одному.
- `FR-04.5` Links: href missing на `<a>`, реально битые внутренние ссылки, `sourcePage`, отсутствие доступного пути из discovery; кнопки с JS-навигацией отмечать `needs_review` по HTML-эвристике, не как доказанный URL-дефект.
- `FR-04.6` JSON-LD: JSON parse, `@type` Product/Offer/aggregateRating, допустимость `ratingCount`/`reviewCount`, сравнение цены/currency/availability с backend или видимыми данными, если доступны; результат помечает границы автоматической достоверности.
- `FR-04.7` HTML-сигналы: повторяющиеся `id`, многократный manifest, изображения без атрибутов размера/alt — как quality warning/info, без автоматической SEO-критичности.
- `FR-04.8` Sitemap: присутствие, XML, URL с неверными статусами, несовпадение canonical, missing expected URLs и отсутствующие в discovery страницы.
- `FR-04.9` Для каждого правила определены `ruleId`, условия, исключения, severity default, evidence, confidence, рекомендации и тесты; переопределение severity конфигурацией без удаления фактов.
- `FR-04.10` Для P0 требуется доказанное блокирование ожидаемой индексируемой страницы; иначе максимально P1 или `needs_review`.

### FR-05. Сканирования и история

- `FR-05.1` Запуск вручную из UI и по cron/CLI.
- `FR-05.2` Состояния: `queued`, `running`, `completed`, `incomplete`, `failed`, `interrupted`, `canceled`.
- `FR-05.3` Сохранение прогресса на диск (checkpoint), без обязательной БД; атомарная запись метаданных, периодическое сохранение очереди.
- `FR-05.4` Не допускать двух одновременных сканов одного проекта; для разных проектов — ограниченный общий пул.
- `FR-05.5` Сравнение запусков по стабильному fingerprint `projectId|ruleId|canonicalizedTarget|entityId(optional)`; статусы `new`, `persisting`, `resolved`, `unknown` при неполном втором скане.
- `FR-05.6` Хранение и удаление по политике retention (количество последних запусков или дни), экспорт файлов перед удалением.

### FR-06. Веб-панель

- `FR-06.1` Авторизация администратора и безопасная сессия; приложение не должно публиковать отчёты анонимно.
- `FR-06.2` Главная: проекты, последний запуск, coverage, P0/P1/P2/info/needs_review, динамика.
- `FR-06.3` Проект: конфигурация, запуск, остановка, история, состояние очереди, ошибки источников, скачивание файлов.
- `FR-06.4` Реестр находок: фильтры severity, status, ruleId, source, entity type, строковый поиск URL, pagination/sorting.
- `FR-06.5` Детальная карточка: воспроизведение, expected vs actual, response chain, source entity, evidence (всегда escaped), советы и граница уверенности.
- `FR-06.6` Сравнение двух запусков и экспорт delta.
- `FR-06.7` Страница настроек и health/status; длинные операции выполняются в worker, не в веб-запросе.

### FR-07. Отчёты и экспорт

- `FR-07.1` Для каждого запуска: `manifest.json`, `urls.jsonl`, `findings.jsonl`, `summary.json`, `findings.csv`, `report.html`.
- `FR-07.2` HTML отчёт самодостаточен (без внешних CDN), отражает полноту скана и не исполняет HTML из целевого сайта.
- `FR-07.3` CSV UTF-8 с BOM для Excel по настройке; экранировать значения, начинающиеся с `=`, `+`, `-`, `@`, чтобы исключить CSV formula injection.
- `FR-07.4` Ошибки доступа к backend/HTTP выделены в `scanner_errors.jsonl` и не подменяют SEO-факты.
- `FR-07.5` В файлах и UI запрещены токены API, cookies, Authorization headers, персональные данные из ответа (кроме явно необходимых структурных полей).

## 7. Приоритеты и классификация находок

- **P0 / Blocker:** источник ожидаемых индексируемых URL говорит «должна быть 200», а подтверждённый HTTP-ответ — 404/410 (после контролируемого повтора); систематическое `noindex` на обязательных посадочных страницах; масштабный 5xx. Не путать с индексом Google.
- **P1 / High:** недоступные из ссылок страницы, неверный canonical или sitemap для важных URL, redirect loop, JSON-LD со сломанными ключевыми требованиями.
- **P2 / Medium:** дубли title/description, технические предупреждения, некоторые метатеги.
- **INFO / Low:** декоративные alt, лишний manifest, рекомендация по структуре HTML и др.
- **NEEDS_REVIEW:** сканер не может подтвердить бизнес-смысл, состояние backend неизвестно, подозрение на soft 404 без достоверной семантики, кнопка «похожа на переход», различия User-Agent без подтверждения от реального бота.

Severities — дефолты правил; окончательная критичность зависит от `expectedIndexable`, типа страницы и масштаба. Все автоматические выводы допускают «неизвестно».

## 8. Подключение backend: принципиальные условия

HSI не знает о Битриксе, Shopify или Pimcore. Общий read-only **Entity Feed Contract v1** содержит объекты `product`, `category`, `page` с устойчивым ID, абсолютным публичным URL, состоянием публикации и опциональными ожидаемыми данными. Источник может выдавать feed напрямую или через отдельный adapter/proxy, но ядро знает только JSON-контракт.

Нельзя выводить «товар должен быть на сайте» только из наличия записи в каталоге CMS. Источник обязан сообщить состояние **публикации на витрине**, учитывая расписания, каналы, видимость, выключенные товары и правила URL. Если состояние неизвестно — `needs_review`.

Аутентификация backend — read-only HTTP Bearer через `${ENV_VAR}`; не включать токен в проектный YAML, URL, логи или отчёты. Сбоем API нельзя объяснять удаление товара.

## 9. Нефункциональные требования

- **Безопасность:** защита от SSRF (allowlist хостов, запрет IP private/loopback/link-local, DNS rebinding и повторная проверка каждого редиректа), HTTPS и валидация сертификата; UI за reverse proxy/TLS, авторизация, CSRF, sanitization, XSS/CSV injection защита. Локальные/private backend API — только через отдельный явно доверенный режим с сетевой политикой, не по умолчанию.
- **Производительность:** потоковая обработка XML/HTML, bounded concurrency, disk-backed queue, отсутствие загрузки всего каталога и всех ответов HTML в память. Полный охват, лимиты — явные и контролируемые, не молчаливый truncation.
- **Надёжность:** lock на проект, атомарные файлы (`.tmp`→rename), checkpoint, graceful shutdown, чёткое состояние incomplete/failed, контролируемые retries.
- **Наблюдаемость:** structured JSON logs, job ID, source-coverage, health endpoint, стабильные IDs правил.
- **Доступность:** веб-панель на русском, таблицы со страницами, поиск, доступные подписи элементов управления; без обязательного внешнего CDN.
- **Совместимость:** Docker Compose на Linux x86_64/arm64, Node.js LTS (точную major версию фиксирует lockfile на старте). Архитектура без предположений о React/Next.js у сканируемого сайта.
- **Конфиденциальность:** HTML сниппеты лимитированы; cookie, данные форм и чувствительные URL-параметры редактируются/маскируются; архивы не должны быть публично доступны по статическому URL.

## 10. План релизов и ограничения

**MVP:** standalone + entity-feed REST/JSON, HTTP/SSR анализ, основная библиотека правил, полнота каталога, JSONL/CSV/HTML, file-based история, Docker, веб-панель, расписание, regression fixtures.

**V1.1:** расширенный импорт нескольких feeds, batch concurrency/UI, дополнительные JSON-LD types, улучшенный diff и удобный экспорт Jira.

**V2:** браузерный рендеринг Playwright (JS, hydration, визуальные дефекты), Lighthouse, официальные GSC/Яндекс.Вебмастер интеграции, оповещения.

Фактически «полная диагностика 18 пунктов аудита» невозможна в MVP: измерение Core Web Vitals, реальные серверные ответы Googlebot/Яндекс.Бота, оценка UX и бизнес-качества контента остаются вне границ. Пользователь должен видеть это в интерфейсе.

## 11. Риски и предположения

- **(!!!!!)** API разных проектов не содержит готового публичного URL: понадобится отдельная карта маршрутов или adapter-transform.
- **(!!!!!)** На некоторых headless-сайтах контент появляется только после JS. HSI вернёт `SSR_CONTENT_MISSING / needs_review`, а не сделает вывод, что страница непременно отсутствует в индексе.
- **(!!!!!)** Сайты с большим количеством фасетных URL могут иметь «бесконечное» пространство обхода. Нужны согласованные правила параметров, исключений и глубины.
- **(!!!!!)** Backend и фронтенд могут быть отделены CDN/WAF; статус из контейнера не равен состоянию на инфраструктуре поисковика.
- Файловое хранение без БД увеличивает сложность индексов, поиска и конкурирующих операций. Для MVP предусмотрены per-run summary + сгенерированные компактные индексы, без записи в SQLite.
- Сканы каталогов потенциально создают нагрузку. Дефолт — мягкий безопасный профиль, индикатор оценочного времени, возможность ограничить скорость и приостановить.

## 12. Контрольные сценарии SABOSPORTS

Эти кейсы используются как **фикстуры** и тесты поведения, а не как зашитые в программу пути:

1. Публичный товар `deadlift-ii-white` возвращает 200 обычному браузеру, тогда как отчёт вебмастеров описывал 404. HSI должен подтвердить только свой HTTP-ответ и написать, что реальный ответ робота неизвестен.
2. В Product JSON-LD товарного файла есть `aggregateRating.ratingValue=5` без количества отзывов — показать `PRODUCT_RATING_COUNT_MISSING` с ссылкой на элемент JSON-LD.
3. Консистентные URL без слеша + корректный canonical без слеша — не считать ошибкой только из-за предпочтения аудитора.
4. Несуществующий slug категории, который фактически отдаёт 200 с общим каталогом: при активном backend feed это `EXPECTED_ENTITY_MISSING/UNKNOWN_ROUTE_RETURNS_200` (если невозможно доказать семантику — `needs_review`).
5. Дубли `id` и manifest — quality warning/low, а не P0.
6. Сохранённый HTML после client navigation не является доказательством исходного SSR: HSI обязан запрашивать и анализировать исходный HTTP документ самостоятельно.

## 13. Приёмка продукта (Definition of Done)

- Все обязательные сценарии AC-01…AC-28 из технической спецификации проходят в CI и на демонстрационном Docker Compose.
- Прогон демонстрационного набора с 404/200/308/canonical/JSON-LD/links показывает ожидаемые результаты и подтверждающие данные.
- Два разнородных проекта (заглушка Next.js + статический сайт на ином стеке) сканируются одним и тем же ядром без изменения исходного кода (только config/feed).
- Приостановленный скан можно продолжить; HTML/CSV безопасны при враждебных значениях.
- Есть эксплуатационная документация: настройка DNS/доменов, секретов, reverse proxy/TLS, cron, backup/retention, пределы анализа, troubleshooting.

## 14. Открытые решения, которые не блокируют проектирование

- **(!!!!!)** Допустимый максимальный объём страниц на проект (предлагаемый soft-limit: 100 000 URL с ручным подтверждением увеличения; превышение — явный `incomplete`, не молчаливое отсечение).
- **(!!!!!)** Тип auth веб-панели (для MVP заложен local-admin с паролем через ENV, hash Argon2id и сессией).
- **(!!!!!)** Топология доступа контейнера к backend API, включая приватные адреса: по умолчанию только публичные HTTPS домены allowlist.
- **(!!!!!)** Средний размер каталога и требуемое время полного скана; дефолт `2 concurrent`, `1 req/s/host` как безопасный стартовый параметр, корректируется после пилота.
